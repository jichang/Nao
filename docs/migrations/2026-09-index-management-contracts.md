# 2026-09 index management contracts

## Scope

- New generic contract: `KnowledgeIndexManagement<'Record>`.
- New composed capabilities: `ManagedKnowledgeVectorIndex` and
  `ManagedKnowledgeLexicalIndex`.
- New validated health, migration-plan, backup, and rebuild-result records.
- Current Nao-owned markers remain version 1.

## Control plane

Index management is distinct from retrieval. Implementations expose:

1. idempotent index creation;
2. health and searchable-record reporting;
3. revision-based migration planning and application;
4. atomic namespace rebuild;
5. typed owner-scoped backup;
6. owner-validated restore.

Creation, health, and migration do not accept an end-user `AuthorizationScope`. They execute
under deployment-controlled adapter credentials and belong in an administrative control plane.
Hosts must not expose them directly through an untrusted request.

## Data operations

Rebuild, backup, and restore require an authenticated `AuthorizationScope` and an explicit index
namespace. A backup binds:

- the v1 backup marker;
- namespace;
- complete `AuthorizationIdentity`;
- creation time;
- validated vector or lexical records.

Restore must call `KnowledgeIndexBackup.requireOwner` before mutation. It must then validate every
record using the adapter's normal profile, document, and ownership checks.

Backups are typed rather than vendor-native byte dumps. This keeps compatibility and
authorization checks visible, but it also means backups can contain source text, metadata, and
vectors. Persist and transport them with controls appropriate for the source data classification.

## Migration semantics

Schema migration plans use content-hash revisions rather than increasing the Nao-owned v1 marker
while the project is unreleased. A plan cannot target the already-current revision and states
whether searchable records must be rebuilt.

Applying a plan generated by another adapter instance, profile, or current revision must fail
rather than silently succeeding. Implementations should use database transactions or an explicit
staging-and-swap protocol.

## Rebuild and restore

Successful rebuild and restore operations report previous and current searchable row counts and
completion time. Counts cannot be negative. Implementations must make the replacement atomic or
retain enough state for deterministic compensation; a failed replacement must not report
success.

`KnowledgeIndexRebuild.vectorAsync` and `KnowledgeIndexRebuild.lexicalAsync` are the executable
rebuild operations for the data-plane capabilities. They submit one mutation containing:

- every authoritative record to restore;
- a namespace-wide typed deletion filter;
- no source retirements.

The adapter deletes the complete owner/namespace selection and inserts the authoritative records
inside one transaction. The committed mutation evidence becomes the rebuild's previous/current
record counts and completion time. Empty authoritative record sets are supported and atomically
clear the namespace.

```fsharp
let! result =
    KnowledgeIndexRebuild.vectorAsync
        vectorIndex
        authorization
        namespaceName
        authoritativeRecords
        cancellationToken
```

The normal adapter checks still apply. Cross-owner records, records from another namespace,
incompatible embedding profiles, duplicate chunks, or records from retired sources fail the
rebuild and preserve the prior searchable state.

## Rollback

Remove management composition from adapter construction and continue using the query capability
directly. Do not convert typed backups into unchecked provider-specific payloads or restore them
without owner validation.
